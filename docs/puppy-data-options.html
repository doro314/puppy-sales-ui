  1. Every mistake is silent. Nothing between your editor and the live site checks a single value. The costliest one — an available puppy shown as Adopted with no way to inquire — is one capital letter away, and SPEC.md in this repo still documents true | false | null, the exact format that triggers it.
  2. The data's shape is the page's layout. PuppyDetails renders Object.entries(details): key order is display order, key names are labels (weightAsOf → “Weight As Of”; specialMarkings was renamed in b7cdc21 just to change a label), and the number of keys picks the layout. Six facts flips a puppy into the litter grid, which has no status badge.
  3. The litter is a nav tab. Breed, parents and dates live on the record whose id is "home", and ImageGallery finds them by that id. So readiness is site-wide: the day you type in the next litter's ready date, every unsold puppy from this litter turns “Available Soon”. Two litters can't be on the site at once — which is exactly the situation “new puppies” creates.
  4. Same fact, two fields. icon restates sex. id, name and folder say one thing three ways. litterSize restates the puppy count. mom: "Coco / Havapoo" packs two facts into one string, which is why the parents card reads “Coco / Havapoo”.
  5. Parents live in code. /Leo.jpg and /Coco.jpg are hard-coded in ImageGallery.jsx. A litter with a different sire is a code change, not a data change.
  6. Photos ship at camera size. 2000–4284 px originals, about 0.8 MB each after the build's compression, used for the 73 px thumbnails too. Opening Bella on a phone downloads 7.9 MB (§04).
  7. Photo order is a file-naming trick. Photos sort alphabetically, so Bella, Olive and Pepper had recent shots renamed A1–A3 to lead. Brownie and Jasper didn't, so their first photo is a two-week-old pup on a patterned blanket.
  8. The written instructions point backwards. README.md is Create React App boilerplate plus a Supabase plan for a schema two refactors old (id: 'all', available boolean). SPEC.md describes the boolean.

02 · Where the data lives

Is this the best system?

Four homes for the same records, from fewest to most moving parts. Each answers three questions differently: who edits it, with what tool, and what stops a mistake.

Pick oneSRC-1 · SRC-2 · SRC-3 · SRC-4

SRC-1

Typed module

Smallest change of the four.

Keep puppies.jsx as code and describe its shape in JSDoc comments. With // @ts-check at the top, VS Code's built-in TypeScript checker underlines a value that isn't in the list.

src/data/puppies.jsxsketch
// @ts-check
/** @typedef {'available'|'reserved'|'adopted'} Status */
/** @typedef {'female'|'male'} Sex */
/** @typedef {{ slug: string, name: string, sex: Sex,
               status: Status, color?: string[] }} Puppy */

/** @type {Litter[]} */
const litters = [
  { id: '2026-06-coco-leo', puppies: [
    { slug: 'bella', name: 'Bella', sex: 'female',
      status: 'available' },  // comments still work
  ]},
];
+ Comments and trailing commas keep working; no format change.
− The allowed values live in a comment block, in a second dialect (JSDoc) you have to keep learning.
− Type errors are editor hints only: vite build doesn't type-check, so a bad value still deploys unless DATA-1 runs.
− Only JavaScript can read it.

SRC-4

Database Not recommended

Most moving parts; the only one where edits skip the deploy.

The plan in README.md: litters and puppies tables in Supabase, photos in a storage bucket, all fetched when the page loads.

+ Edits go live without a deploy; there's a table editor in the browser.
− Supabase pauses free projects after 7 days of low activity. That's the weeks between litters: the site would show an error until someone restores the project.
− Loading and error states on every page, keys and access rules to manage, and photos lose build-time resizing.
− The README's plan targets a schema two refactors old; it would be rewritten before it was built.
− The largest change by far — for about six records, twice a year.
The answer to “is this the best system?”: keeping the data in the repo is right. At six puppies twice a year, git is the database, a push is the deploy (Cloudflare builds main), and the commit log is the history — free, nothing to pause, nothing to log in to. What's missing is a written list of allowed values and something that enforces it. SRC-2 adds the first and DATA-1 the second, without adding a service.
Holds whichever wins: components keep importing query functions from src/data/puppies.jsx and never the raw records (CLAUDE.md › Data Layer). That's what keeps SRC-2 → SRC-4 a one-file swap if a database ever earns its keep.

03 · What a litter is

The day the next litter arrives

Three shapes for the same five puppies. The test that separates them is a likely day: Olive is still available when Coco's next litter is born.

LIT-1

Overwrite Fails the test

Least change.

Rename the "home" record to a real litter and structure its parents, but keep one litter. When the next one arrives, replace it.

litters.jsonshape
{
  "litter": { "breed": "Havapoo", "born": "2026-06-02",
              "readyDate": "2026-07-28" },
  "puppies": [ { "slug": "olive", "status": "available" } ]
}
+ Smallest edit to today's code.
− The test fails: entering the new litter's dates either deletes Olive or turns her “Available soon” at six months old.
− Past litters live on only in git history.

LIT-2

Litter list ★ Recommended

Passes the test with nothing to keep in sync.

Each litter carries its own parents, dates and care log, and its puppies sit inside it, so there is no id to match. The site shows every litter with "listed": true, newest first.

litters.jsonshape — full file in §07
{
  "litters": [
    { "id": "2027-01-coco-leo", "listed": true,
      "due": "2027-01-12", "puppies": [] },
    { "id": "2026-06-coco-leo", "listed": true,
      "born": "2026-06-02", "readyDate": "2026-07-28",
      "puppies": [ { "slug": "olive", "status": "available" } ] }
  ]
}
+ The test passes: Olive keeps her own litter's dates while the next litter shows as expecting.
+ Retiring a litter is "listed": false — nothing deleted, photos included.
+ Parents and their photos are data; a new sire is a JSON edit.
− Puppies sit one level deeper in the file.
− Photo folders move to src/images/<litter>/<puppy>/ — one git mv per folder, once. Coco.jpg and Leo.jpg move from public/ to src/images/parents/ so they get resized too.
− ImageGallery and PuppyDetails stop reading the "home" record.

LIT-3

Relational Not recommended

The database shape, in a hand-edited file.

Litters and puppies as two flat lists; each puppy names its litter.

litters.jsonshape
{
  "litters": [ { "id": "2026-06-coco-leo", "born": "2026-06-02" } ],
  "puppies": [ { "slug": "olive",
                 "litter": "2026-06-coco-leo" } ]
}
+ Passes the test, and matches database tables — the right shape if SRC-4 ever happens.
− Every puppy carries an id that must match another record: the kind of must-agree pair this doc is removing. In a file you edit by hand, nesting makes the link impossible to get wrong.

08 · Cleanups

Worth doing under any option

Small and independent — take all, some, or none. Name them by code.

  1. Stop documenting the value that breaks the page. SPEC.md and the README's Supabase plan both say available is a boolean; true renders “Adopted” with no inquiry button. Delete SPEC.md and correct the README, even if DATA-5 isn't taken.
  2. Accept .webp and .avif photos, and warn about .heic. The glob takes only jpg/jpeg/png/gif, so anything else is dropped without a word. Browsers can't show HEIC, so that one gets a warning rather than support.
  3. Resolved Nov 24 — move systemX-logo.png out of src/images/home/. It was a stray file from another project and has been deleted, so nothing in that folder will play as a slide by mistake.
  4. Count the puppies instead of storing litterSize. Keep the field only for litters where not every puppy is listed, and warn when it's smaller than the list.

Build order

  1. DATA-1 with the §07 files, before the site reads them. The schema, the converted litters.json and the checker land together, wired into build, dev and test, while the pages still read puppies.jsx. The checker's first job is the conversion itself, and the live site doesn't change. (It can't go first against today's file: what it checks is the new format.)
  2. SRC-2 + LIT-2: the site switches over. A git mv per photo folder, the query functions in puppies.jsx rewritten to read litters, the old array deleted. The query functions still hand today's pages what they expect, so every page looks as it does now apart from the casing fixes — the proof that the conversion is right. DFIX-4 comes with it: the converted file already drops litterSize.
  3. IMG-1, with DFIX-2. Alone, so a visual regression is easy to bisect. The glob changes here anyway, so .webp and .avif join it.
  4. DATA-2, -3, -4. Facts list, weight log, cover — the display side of the new fields.
  5. DATA-5 and DFIX-1 last. The manual describes what was actually built.
  6. The tutorial, once everything is built. A plain-language guide to managing litters, with a small working editor to practise in — written last, so it teaches the real thing.

The design doc's steps read this data, so they start after step 2. site-design-options.html §07 has both docs' steps as one sequence.

Before you start — three ways this ships broken. The Mac ignores the case of file names and Cloudflare's Linux build doesn't, so the checker compares cover, parent photos and folder names with each folder's real listing, never a does-this-file-exist call — otherwise a cover written IMG_1876.jpeg for a file saved as IMG_1876.JPEG passes on the Mac and fails the deploy. · Every photo folder holds a .DS_Store, and src/images/parents/ sits beside the litter folders: the checker and the loader skip dotfiles and never read parents/ as a litter. · The 16 tests mock today's data shape. Step 2 keeps them passing through the query functions; each later step that replaces a component replaces its tests.
The one thing I'd flag: SRC-2's help is VS Code's. Edit litters.json in GitHub's web editor or on a phone and you get no suggestions and no underlines — only the checker's verdict when the build runs. If anyone besides you will be updating puppies, that's the real argument for SRC-3, and it reverses independently: the schema and checker carry over to a sheet unchanged.
